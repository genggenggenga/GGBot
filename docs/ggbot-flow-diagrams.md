# GGBot 核心链路与流程图

> 本文整理当前 GGBot 从用户请求、意图识别、状态管理、Agent 执行、RAG 检索、知识库构建到响应持久化的主要流程。
>
> 文档以当前工作区代码为准：正常 `/chat` 请求使用 `CustomerAgentRuntime`；工具通过内部 RPC 调用；只有 `AfterSalesAgent` 注入 Skill。旧版 `AgentOrchestrator` 和 stdio MCP 不属于当前主链路。

## 1. 完整请求链路

```text
┌──────────────────────────────┐
│ 用户发送消息                 │
│ message / user_id / conv_id  │
└──────────────┬───────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ FastAPI POST /chat                          │
│                                             │
│ 未提供 conv_id → 生成 UUID                  │
│ 服务未就绪   → HTTP 503                     │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ RedisConversationLockManager                │
│                                             │
│ 按 user_id + conv_id 获取分布式锁           │
│ ├─ 防止同一会话并发修改状态                 │
│ ├─ 自动续租                                 │
│ └─ 等待超时 → HTTP 409                      │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ MemoryManager.get_context()                 │
│                                             │
│ Redis                                       │
│ ├─ 当前会话最近消息                         │
│ ├─ 会话摘要                                 │
│ └─ DialogueState                            │
│                                             │
│ ChromaDB                                    │
│ ├─ 跨会话情景记忆                           │
│ └─ 用户长期画像                             │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ 上下文组装                                  │
│                                             │
│ history = 最近 5 条消息                     │
│ agent_context = DialogueState               │
│               + 最近消息                   │
│               + 会话摘要                   │
│               + 相关历史                   │
│               + 用户画像                   │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ CustomerAgentRuntime.run()                  │
│                                             │
│ 1. 生成 trace_id                            │
│ 2. fork 独立 TurnEngine                     │
│ 3. 从 Redis 恢复 DialogueState              │
│ 4. 推导本轮可恢复的 ExecutionState          │
└──────────────┬──────────────────────────────┘

┌─────────────────────────────────────────────┐
│ IntentRecognizer.recognize_structured()     │
│                                             │
│ Fast Track → 必要时单次结构化 LLM           │

└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ DialogueStateTracker.update()               │
│                                             │

│ 处理意图切换、确认和拒绝                    │
│ 计算 required_slots / missing_slots         │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ TurnEngine 有界状态循环，最多 6 步          │
│ 每次状态迁移后立即保存 DialogueState        │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ UNDERSTANDING                               │
│   ├─ 意图不明确/缺槽位 → CLARIFYING         │
│   └─ 信息完整           → ROUTING            │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ Router：确定性路由，不调用 LLM              │
│                                             │
│ FAQ/政策/技术/账户 → KnowledgeAgent         │
│ 订单查询           → OrderAgent             │
│ 物流查询           → LogisticsAgent         │
│ 售后/投诉/转人工   → AfterSalesAgent        │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ DomainAgentRuntime                          │
│                                             │
│ 复合意图拆成多个 goal 并按顺序执行          │
│ 同一订单的 query_order Observation 可复用   │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ AgentResult                                 │
│                                             │
│ response / observations / citations         │
│ pending_action / missing_slots / error       │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ 结果分支                                    │
│                                             │
│ 成功     → ResponsePolisher → COMPLETED     │
│ 缺槽位   → CLARIFYING → 等待下一轮          │
│ 写操作   → AWAITING_CONFIRMATION            │
│ 失败     → FAILED → HandoffPackage          │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ 收尾与持久化                                │
│                                             │
│ ├─ 写入用户消息和助手回复                   │
│ ├─ 必要时压缩会话摘要                       │
│ ├─ 更新稳定用户画像                         │
│ ├─ 完成/转人工时写入情景记忆                │
│ ├─ 记录 Trace 与耗时                        │
│ └─ 释放 Redis 会话锁                        │
└──────────────┬──────────────────────────────┘
               ▼
┌─────────────────────────────────────────────┐
│ 返回 ChatResponse                           │
│                                             │
│ response / intent / agent_type              │
│ status / missing_slots / citations          │
│ escalated / trace_id / latency_ms           │
└─────────────────────────────────────────────┘
```

### 解读

- 会话锁覆盖上下文读取、状态执行、消息写回和事件记录，保证同一会话的整轮提交串行化。
- `DialogueState` 保存跨轮业务状态，`TurnContext` 保存本轮执行状态。
- `CLARIFYING` 和 `AWAITING_CONFIRMATION` 是暂停点；`COMPLETED` 和 `FAILED` 是终态。
- 复合意图不是并行执行，而是由 `DomainAgentRuntime` 按 goal 顺序执行。

## 2. 单次提问的全分支流程

```text
┌─────────────────────────────────────┐
│ 用户输入                            │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ NLU Fast Track                     │
│                                     │
│ 意图 / 多意图 / 订单号 / 物流号     │
│ 确认 / 拒绝 / 切换 / 槽位纠正       │
└──────────────────┬──────────────────┘
                   ▼
          ┌───────────────────┐
          │ 规则能确定结果？  │
          └─────────┬─────────┘
               是   │   否
         ┌──────────┘   └──────────────┐
         ▼                              ▼
┌──────────────────┐        ┌──────────────────────┐
│ 使用规则结果     │        │ 单次结构化 LLM      │
│ 不调用 LLM       │        │                      │
└────────┬─────────┘        │ intents + slots     │
         │                  │ user_act + confidence│
         │                  └──────────┬───────────┘
         └──────────────────┬──────────┘
                            ▼
┌─────────────────────────────────────┐
│ 安全门禁                            │
│                                     │
│ 普通意图 confidence ≥ 0.65          │
│ 操作意图 confidence ≥ 0.85          │
│ LLM 槽位必须来自原文并通过业务验证  │
└──────────────────┬──────────────────┘
                   ▼
          ┌───────────────────┐
          │ 置信度足够？      │
          └─────────┬─────────┘
               否   │   是
        ┌───────────┘   └──────────────┐
        ▼                               ▼
┌──────────────────────┐    ┌──────────────────────┐
│ 意图澄清             │    │ 更新 DialogueState │
│ status=awaiting_user │    └──────────┬───────────┘
└──────────────────────┘               ▼
                         ┌─────────────────────────┐
                         │ 当前有待确认写操作？    │
                         └────────────┬────────────┘
                                否   │   是
                           ┌─────────┘   └─────────┐
                           │                       ▼
                           │             ┌──────────────────┐
                           │             │ 本轮 UserAct     │
                           │             └────────┬─────────┘
                           │        ┌─────────────┼─────────────┐
                           │        ▼             ▼             ▼
                           │      CONFIRM       REJECT       新意图
                           │        │             │             │
                           │        ▼             ▼             ▼
                           │    执行原操作     取消原操作    澄清是否切换
                           │                                  或显式 SWITCH
                           └──────────────┬─────────────────────┘
                                          ▼
                              ┌───────────────────┐
                              │ 缺少必填槽位？    │
                              └─────────┬─────────┘
                                   是  │  否
                         ┌─────────────┘  └────────────┐
                         ▼                              ▼
              ┌────────────────────┐       ┌────────────────────┐
              │ 槽位澄清           │       │ 确定性 Router      │
              │                    │       └──────────┬─────────┘
              │ 追问订单号/物流号  │                  ▼
              │ 等待下一轮         │       ┌────────────────────┐
              └────────────────────┘       │ 执行领域 Agent     │
                                           └──────────┬─────────┘
                                                      ▼
                                    ┌─────────────────┼─────────────────┐
                                    ▼                 ▼                 ▼
                                  成功             PendingAction       失败
                                    │                 │                 │
                                    ▼                 ▼                 ▼
                              COMPLETED      等待确认/拒绝       FAILED/Handoff
```

### 解读

- 当已有写操作等待确认时，“确认”和“取消”优先解释为 `UserAct`，不会重新识别为普通业务意图。
- 用户提出新目标但未明确切换时，系统不会静默丢弃待确认动作，而是先询问是否取消并切换。
- 缺少订单号或物流号时不会进入 Agent 工具执行，状态先进入 `CLARIFYING`。
- Agent 失败、非法状态迁移、缺失 handler 或超过步数上限都会生成结构化 `HandoffPackage`。

## 3. 写操作跨轮确认流程

```text
┌──────────────────────────────┐
│ Agent 选择 WRITE 工具        │
│ refund/return/cancel/ticket  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 创建 PendingAction           │
│                              │
│ action_id                    │
│ tool_name                    │
│ frozen arguments             │
│ requires_confirmation=true   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 保存 DialogueState          │
│ confirmation_status=pending  │
│ 不执行真实写工具             │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 请求用户确认                 │
│ status=awaiting_user         │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 下一轮 Fast Track            │
│ 识别 CONFIRM / REJECT        │
└──────────────┬───────────────┘
               ▼
       ┌───────────────┐
       │ 用户行为？    │
       └───────┬───────┘
          拒绝 │ 确认
       ┌───────┘ └─────────────────┐
       ▼                           ▼
┌────────────────────┐   ┌──────────────────────────┐
│ REJECTED           │   │ CONFIRMED                │
│                    │   │                          │
│ 清除 PendingAction │   │ 恢复冻结的 action_id    │
│ 不执行写工具       │   │ tool_name / arguments   │
└─────────┬──────────┘   └────────────┬─────────────┘
          │                           ▼
          │                ┌──────────────────────────┐
          │                │ ToolRegistry            │
          │                │                          │
          │                │ Agent 白名单            │
          │                │ WRITE 确认门禁          │
          │                │ 参数 Schema             │
          │                └────────────┬─────────────┘
          │                             ▼
          │                ┌──────────────────────────┐
          │                │ Redis 幂等仓库           │
          │                │ action_id + 参数指纹     │
          │                └────────────┬─────────────┘
          │                             ▼
          │                ┌──────────────────────────┐
          │                │ 内部 RPC 执行写操作      │
          │                └────────────┬─────────────┘
          └─────────────────────────────┤
                                        ▼
                              ┌──────────────────────┐
                              │ RESPONDING          │
                              │ → COMPLETED         │
                              └──────────────────────┘
```

### 解读

- 模型只能提出写操作建议，不能直接执行副作用。
- `PendingAction` 冻结动作参数，防止用户确认时重新规划成不同操作。
- `action_id` 同时贯穿对话状态、确认门禁、RPC 请求和 Redis 幂等仓库。
- 用户拒绝后不会换用另一个写工具继续尝试。

## 4. RAG 在线检索流程

```text
┌────────────────────────────────────┐
│ KnowledgeAgent.execute()           │
│ message + history + DialogueState  │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ QueryPlanner.plan()                │
│                                    │
│ ├─ 消解“这个/刚才的”等指代        │
│ ├─ 生成 standalone_query           │
│ ├─ 生成 alternative_queries       │
│ ├─ 保护订单号、版本号等标识符      │
│ └─ 最多保留 3 个查询               │
│                                    │
│ LLM 失败/低置信度 → 使用原始查询   │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ ToolRegistry.call(rag_search)      │
│ 白名单 / Schema / 30s 超时 / 缓存  │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ RetrievalFilter.current()          │
│                                    │
│ status=published                   │
│ effective_at <= as_of              │
│ expires_at > as_of                 │
└─────────────────┬──────────────────┘
                  ▼
         ┌────────┴─────────┐
         ▼                  ▼
┌─────────────────┐  ┌─────────────────┐
│ Dense Retrieval │  │ Sparse Retrieval│
│                 │  │                 │
│ ChromaDB        │  │ 内存 BM25       │
│ Cosine Search   │  │ 关键词匹配      │
│ candidate_k=20  │  │ candidate_k=20  │
└────────┬────────┘  └────────┬────────┘
         └──────────┬─────────┘
                    ▼
┌────────────────────────────────────┐
│ Reciprocal Rank Fusion             │
│                                    │
│ 合并多查询、Dense、BM25 排名       │
│ 按 chunk_id 去重                   │
│ RRF score = Σ 1 / (60 + rank)      │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ Reranker                           │
│ query + candidate chunks           │
│ → relevance_score → 重新排序       │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ 相关性门禁                         │
│                                    │
│ dense=0.2 / hybrid=0.01 / rerank=0.1│
└─────────────────┬──────────────────┘
            ┌─────┴─────┐
       不满足           满足
          ▼               ▼
┌─────────────────┐  ┌──────────────────────┐
│ 拒绝回答        │  │ Top K，默认 5       │
│ answered=false  │  │ 生成 Citation       │
└─────────────────┘  └──────────┬───────────┘
                                ▼
┌────────────────────────────────────┐
│ 是否询问历史变化？                 │
│ 最近/以前/更新/变化/区别           │
└─────────────────┬──────────────────┘
            ┌─────┴─────┐
           否            是
           │             ▼
           │  ┌──────────────────────────┐
           │  │ 回查同 knowledge_id      │
           │  │ 的上一有效版本           │
           │  │ 计算 added / removed     │
           │  └────────────┬─────────────┘
           └───────────────┤
                           ▼
┌────────────────────────────────────┐
│ RAGAnswerGenerator                 │
│                                    │
│ 最多 5 个 chunk                    │
│ 最多 1800 context tokens           │
│ 结构化生成带引用回答               │
└─────────────────┬──────────────────┘
                  ▼
┌────────────────────────────────────┐
│ 回答安全校验                       │
│                                    │
│ 每段必须引用证据                   │
│ 引用必须真实存在                   │
│ 禁止编造数字和业务标识符           │
└─────────────────┬──────────────────┘
            ┌─────┴─────┐
        校验失败        校验通过
            ▼             ▼
┌─────────────────┐  ┌──────────────────────┐
│ 抽取式回答降级  │  │ response + citations│
│ 或证据不足拒答  │  └──────────────────────┘
└─────────────────┘
```

### 解读

- 原问题始终参与召回，避免 QueryPlanner 改写偏移导致零召回。
- Dense、RRF 和 Reranker 分别使用不同量纲的阈值。
- Citation 来自检索元数据，不由生成模型自行编造。
- 生成答案失败时可以降级为首个有效 chunk 的抽取式回答；证据不足时明确拒答。

## 5. 知识库构建与版本管理

```text

                  ▼

└────────────────────────────────────┘
```

### 版本发布与撤销

```text
┌──────────────────────────────┐
│ publish_version              │
│                              │
│ status=published             │
│ 校验 effective/expires 时间  │
└──────────────┬───────────────┘
               │
               ├───────────────┐
               ▼               ▼
┌────────────────────┐  ┌────────────────────┐
│ rebuild timeline   │  │ revoke_version     │
│ 设置版本有效区间   │  │ status=revoked     │
│ 标记最新 current   │  │ is_current=false   │
└─────────┬──────────┘  └─────────┬──────────┘
          └────────────┬───────────┘
                       ▼
             KnowledgeRuntime.refresh()
                       │
                       ▼
                 重建 BM25 索引
```

### 解读

- ChromaDB 是 canonical chunk store，BM25 是可以从 ChromaDB 重建的运行时索引。
- Markdown 保留标题路径，PDF 保留页码，Citation 因而可以追踪到来源位置。
- 版本可见性由状态和时间窗口共同决定，不依赖生成模型判断。

## 6. Multi-Agent 总体架构

```text
┌─────────────────────────────────────┐
│ CustomerAgentRuntime               │
│ DialogueState + intents + context  │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ Router：确定性路由                  │
│                                     │
│ query/policy/technical → Knowledge  │
│ order_query           → Order       │
│ logistics_query       → Logistics   │
│ refund/return/cancel  → AfterSales  │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ DomainAgentRuntime                  │
│                                     │
│ 复合 goal 顺序执行                  │
│ 复用订单 Observation                │
│ PendingAction/失败时停止            │
└───────┬─────────┬─────────┬─────────┘
        ▼         ▼         ▼
  Knowledge     Order    Logistics   AfterSales
  固定 RAG    受限 ReAct 受限 ReAct  Skill+ReAct
```

### Agent 职责

| Agent | 负责意图 | 执行方式 | 是否注入 Skill |
| --- | --- | --- | --- |
| `KnowledgeAgent` | FAQ、政策、技术、账户、问候、反馈 | 固定回复或单次 RAG | 否 |
| `OrderAgent` | 订单状态、商品、支付、发票 | 受限 ReAct，失败后确定性降级 | 否 |
| `LogisticsAgent` | 物流轨迹、预计送达、异常诊断 | 受限 ReAct，失败后确定性降级 | 否 |
| `AfterSalesAgent` | 退款、退货、取消、投诉、转人工 | 售后 Skill + 受限 ReAct + 确认门禁 | 是 |

## 7. KnowledgeAgent

```text
┌─────────────────────────────────────┐
│ KnowledgeAgent                     │
│                                     │
│ 输入：goal/message/state/history   │
│ 只允许调用 rag_search              │
│ 不进入 ReAct，不加载 Skill          │
└──────────────────┬──────────────────┘
                   ▼
         ┌──────────────────┐
         │ 特殊确定性意图？ │
         └────────┬─────────┘
             是   │   否
       ┌──────────┘   └──────────────┐
       ▼                              ▼
┌────────────────────┐    ┌──────────────────────┐
│ greeting/feedback  │    │ QueryPlanner         │
│ /other             │    │ → rag_search        │
│ 直接固定回复       │    │ → AnswerGenerator   │
└────────────────────┘    └──────────┬───────────┘
                                     ▼
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
          无相关证据/证据不足                 有可靠证据
                    │                                 │
                    ▼                                 ▼
          明确拒答或抽取式降级              带 Citation 回答
```

### 解读

- KnowledgeAgent 被设计为固定的一次检索链路，避免 FAQ 场景出现开放式工具循环。
- `greeting`、`feedback` 和 `other` 不访问知识库。
- 时态比较结果由检索工具生成，KnowledgeAgent 负责组织新旧版本差异回答。

```text
                   ▼

       ┌──────────┘   └──────────────┐
       ▼                              ▼
┌────────────────────┐    ┌──────────────────────┐

│ 追问订单号         │    │ 单步选择唯一动作     │
└────────────────────┘    └──────────┬───────────┘
                                     ▼
                        ┌────────────┴────────────┐
                        ▼                         ▼
                 查询所需订单事实              FINISH
                        │                         │

                 Commerce RPC             基于 Observation
                        │                   生成事实回答
                        └────────────┬────────────┘
                                     ▼

```

### 确定性降级

```text
order_id → query_order
              │
              ├─ found=false → 请用户核对订单号
              ├─ 缺少 status → 执行失败
              └─ status 有效 → 返回订单状态
```

### 解读

- OrderAgent 只查询订单事实，不预测物流、退款或到账时间。
- 商品、支付和发票工具只在用户明确询问对应字段时调用。
- 所有工具均为只读工具，不进入用户确认流程。

## 9. LogisticsAgent

```text
┌─────────────────────────────────────┐
│ LogisticsAgent                     │
│                                     │
│ order_id 或 tracking_no 任一即可    │
│                                     │
│ query_order / track_package         │
│ estimate_delivery                   │
│ diagnose_delivery_exception         │
│ rag_search                          │
└──────────────────┬──────────────────┘
                   ▼
       ┌────────────────────────┐
       │ 有订单号或物流单号？   │
       └───────────┬────────────┘
              否   │   是
        ┌──────────┘   └─────────────┐
        ▼                             ▼
┌────────────────────┐    ┌──────────────────────┐
│ CLARIFYING         │    │ ReActPlanner         │
│ 追问订单号或物流号 │    └──────────┬───────────┘
└────────────────────┘               ▼
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
          tracking_no 直接查物流            order_id 先核验订单
                    │                                 │
                    └────────────────┬────────────────┘
                                     ▼
                        ┌────────────────────────┐
                        │ 按问题选择工具         │
                        │                        │
                        │ 进度 → track_package  │
                        │ 时间 → estimate       │
                        │ 异常 → diagnose       │
                        │ 规则 → rag_search     │
                        └───────────┬────────────┘
                                    ▼
                              AgentResult
```

### 确定性降级

```text
tracking_no ──────────────► track_package ─► 回复物流状态

order_id → query_order
             │
             ├─ 未找到 → 返回未找到订单
             └─ 找到   → track_package → 回复物流状态
```

### 解读

- 具体订单和运单事实以业务 RPC 为准，RAG 只解释通用配送规则。
- 预计送达与异常诊断只有在用户问题确实需要时才调用。
- 回复需区分当前扫描状态、系统估计和建议动作。

## 10. AfterSalesAgent

```text
┌─────────────────────────────────────┐
│ AfterSalesAgent                    │
│                                     │
│ refund / return / cancel            │
│ complaint / escalation              │
│ 唯一接入 SkillManager 的 Agent      │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ SkillManager.prompt_for()           │
│ message + agent_type + intent       │
│ → 匹配售后 SOP 软策略               │
│                                     │
│ Skill 不能绕过白名单和确认门禁      │
└──────────────────┬──────────────────┘
                   ▼
        ┌─────────────────────┐
        │ complaint/escalation│
        └──────────┬──────────┘
             是    │    否
       ┌───────────┘    └─────────────┐
       ▼                               ▼
┌────────────────────┐      ┌──────────────────────┐
│ 工单专用流程       │      │ 受限 ReAct          │
│ create_ticket      │      │ 最多 4 步            │
└─────────┬──────────┘      └──────────┬───────────┘
          │                            ▼
          │                 ┌──────────────────────┐
          │                 │ 只读核验阶段         │
          │                 │                      │
          │                 │ query_order         │
          │                 │ evaluate_options    │
          │                 │ refund_quote        │
          │                 └──────────┬───────────┘
          │                            ▼
          │                 ┌──────────────────────┐
          │                 │ 选择匹配的写工具     │
          │                 │                      │
          │                 │ create_refund       │
          │                 │ create_return       │
          │                 │ cancel_order        │
          │                 │ create_ticket       │
          │                 └──────────┬───────────┘
          └──────────────────┬─────────┘
                             ▼
                    创建 PendingAction
                             │
                             ▼
                 AWAITING_CONFIRMATION
                             │
                    ┌────────┴────────┐
                    ▼                 ▼
                  拒绝               确认
                    │                 │
                    ▼                 ▼
                取消操作     确认门禁 + Redis 幂等
                                      │
                                      ▼
                               AfterSales RPC
                                      │
                                      ▼
                              成功 Observation
                                      │
                                      ▼
                                  COMPLETED
```

### 解读

- 投诉和转人工通过确定性工单流程处理，但创建工单仍属于写操作，必须确认。
- ReAct 负责选择退款、退货、取消订单或工单，执行层负责真正的权限和副作用控制。
- Planner 失败时只有退款允许进入退款专用确定性降级；其他售后目标停止自动执行并建议人工处理。
- “申请提交成功”不代表审核通过或资金到账。

## 11. 共享 ReAct 与工具执行内核

```text
┌─────────────────────────────────────┐
│ DialogueState + message             │
│ observations + allowed_tools        │
│ domain policy + optional Skill      │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ ReActPlanner.decide()               │
│ 每次只返回一个结构化 AgentDecision  │
└──────────────────┬──────────────────┘
                   ▼
       ┌───────────┼───────────┬───────────┐
       ▼           ▼           ▼           ▼
     TOOL        FINISH      CLARIFY     HANDOFF
       │           │           │           │
       ▼           ▼           ▼           ▼
  检查工具      生成回答    询问最少信息  建议人工
       │
       ▼
┌─────────────────────────────────────┐
│ READ  → 立即调用                    │
│ WRITE → 创建 PendingAction          │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ ToolRegistry                        │
│                                     │
│ 工具存在性                          │
│ Agent 白名单                        │
│ 参数 Schema                         │
│ 写操作确认门禁                      │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ LocalToolAdapter                    │
│ 超时 / 熔断 / 缓存 / 统计           │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ Internal RPC Client                 │
│ Commerce / Fulfillment / AfterSales │
└──────────────────┬──────────────────┘
                   ▼
              Observation
                   │
                   └────► 下一步 ReAct 或 FINISH
```

### 共享约束

- 每个 ServiceAgent 最多执行 4 步。
- 相同工具和相同参数不得重复调用。
- 工具参数只能来自用户消息、业务状态或成功 Observation。
- 模型不能调用白名单外工具，也不能伪造工具执行结果。
- ReAct 不输出 Chain-of-Thought，只输出 `TOOL / FINISH / CLARIFY / HANDOFF`。

## 12. 典型请求路径

```text
知识咨询：
输入 → 意图识别 → KnowledgeAgent → RAG → 带引用回答

订单查询：
输入 → 提取订单号 → OrderAgent → Commerce RPC → 返回订单事实

物流查询：
输入 → 订单号/物流号 → LogisticsAgent → Fulfillment RPC → 返回物流状态

缺少槽位：
输入 → 识别意图 → missing_slots → CLARIFYING → 等待下一轮

退款申请：
输入 → AfterSalesAgent → 核验订单/资格 → PendingAction
     → 用户确认 → 确认门禁/幂等/RPC → 返回申请结果

拒绝写操作：
PendingAction → 用户拒绝 → 清除动作 → 不调用写工具 → 返回取消提示

切换意图：
当前目标 → 用户显式 SWITCH → 清理待确认动作
         → 保留可跨意图槽位 → 路由新 Agent

执行异常：
Agent/Tool 失败 → FAILED → HandoffPackage → 转人工提示
```
